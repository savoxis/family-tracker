# Family Tracker (Kitchen Board)

Touch-first family board for a kitchen screen: per-kid chores and routines with stars, a reward shop, calendar, dinner plan, groceries, timers, countdowns and notes. No accounts, no subscription.

```
web/       the whole UI, one index.html plus bundled fonts (no internet needed)
server/    zero-dependency Node server: serves web/ and keeps the board in one JSON file
android/   WebView wrapper that bundles web/, or points at the home server
deploy/    UnRAID container template
```

The page picks its storage at load: the home server if `/api/state` answers, otherwise browser storage on that device.

## Run it

```
npm start                      # http://localhost:8080, data in server/data/
npm test
docker compose up -d --build   # port 8080, data in the kitchen-board-data volume
```

Image from CI: `ghcr.io/savoxis/family-tracker:latest` (amd64 and arm64).
UnRAID: copy `deploy/unraid/kitchen-board.xml` to `/boot/config/plugins/dockerMan/templates-user/`.

There is no login. Keep it on the home network.

Google Calendar: in Google Calendar open the calendar's Settings and sharing, Integrate calendar, and copy the "Secret address in iCal format". Give it to the server as `ICS_URLS=Family|https://...basic.ics` (several calendars: separate with commas, each as `Label|url`). The server reads it every 15 minutes (`ICS_MINUTES`) and keeps the events from 45 days back to 200 days ahead on the board, repeats included, in `BOARD_TZ` (default: the calendar's own zone). It is read-only: those events have ids starting `gcal-` and edits made to them on the board are overwritten at the next sync. Events typed in on the board are never touched. The link is a secret: keep it in an env file on the host (for Docker, `--env-file`), never in the repo. If it leaks, press Reset next to it in Google Calendar and update the env file.

School calendars and family members: ParentSquare has a Subscribe button on each school's Calendar page that gives a private iCal link (it works without signing in, treat it like a password). Add it to `ICS_URLS` like any calendar. Write the label as `Label@Member` (for example `Brockway@Xander|https://...`) to show that feed's events in that family member's color and under their name. Every synced event carries a source (`google`, `school` or `calendar`, picked from the link's host) and the event screen shows it under "From"; events typed in on the board show "This board".

ParentSquare posts and messages (unofficial, can break): the calendar feed only has dated events, so school posts and the unread message count need a sign-in. Put `PARENTSQUARE_USER`, `PARENTSQUARE_PASSWORD` and `PS_SCHOOLS` (school id and child, like `13482:Xander,13486:Bastian`, the id is in the school's ParentSquare URL) in the env file. The server signs in itself, reads each school's posts page every `PS_MINUTES` (15) and keeps the recent posts and the unread count in the `school` collection, tied to the right child. The board shows a School button (with the unread count), a School card beside Today and Food, and a School view with each child's posts, tags for pinned posts, event dates, forms, RSVPs, sign-ups and files, a short preview, the pictures in the post (shown straight from ParentSquare's public image host when you open a post, tap one for full size), and a link to open the post in ParentSquare. A post from a school's own level goes to that school's child, a class or group post (like a teacher's class) goes to the child too, and district-wide posts are shown once under school-wide. Message contents are never read, only the unread count. It also lists each child's message conversations with the teachers (who wrote, how many messages, when, and a New tag, never the text unless `PS_MESSAGE_PREVIEW=1`; the server only reads the message list and never opens a conversation, because opening one marks it read on ParentSquare) and puts your own appointment sign-ups (like a parent-teacher conference slot) on the calendar as school events in that child's color, plus a Coming up list. `PS_TEACHERS` (like `Xander:Kayla Knight,Bastian:Keli Bruehling`) names each child's teacher. There are no texts for this, ParentSquare already sends its own. It renews the session when it expires, waits at least 10 minutes between sign-ins, and stops after 3 failed sign-ins (the School view then says so) so a wrong password cannot lock the account. The password is only sent to ParentSquare's sign-in form and is never logged. ParentSquare's terms may not allow automated access, so keep the poll gentle.

Messaging a teacher (needs the ParentSquare login above): list each child's teacher in `PS_TEACHERS` (like `Xander:Kayla Knight,Bastian:Keli Bruehling`). The School view then shows a "Message <teacher>" button under that child, with a text box and the 4 digit grown-up PIN from Setup. A message is a reply in the existing conversation if there is one, otherwise a new direct message. The PIN is checked by the server, not the page (5 wrong tries lock it for 10 minutes), only a teacher the server itself found through ParentSquare's recipient search can be written to, `PS_SEND_MAX` (5) caps messages per hour, each send is a single attempt that is never retried, and the message text and PIN are never logged. Note the PIN is stored in the board data like the rest of the settings, so it keeps out kids rather than a determined person on your network.

Reading a conversation: each conversation in the School view has a "Read it here" button that asks for the same PIN and then shows the messages (including your own replies) as chat bubbles. The server checks the PIN (the same lockout as sending), fetches the conversation from ParentSquare, hands it back and keeps nothing: the text is not in the board data, its backups or the logs, and the open conversation hides itself after a few minutes and when the School view is closed. Only conversations the server listed can be opened. Opening a conversation marks it read in ParentSquare (that is what reading it means), so the board only does it when you ask.

Flyer reader (Gemini): set `GEMINI_API_KEY` (a free Google AI Studio key works). Each new public school post is read once, text and up to two pictures, for a one line summary and what to do or bring, which show on the post. Specific dates it finds, including each day of a spirit week with what to wear or do, are added to the calendar as events marked "read by AI" in that child's color, once, skipping anything already on the calendar. Delete one that is wrong and it stays deleted. Results are cached so a post is never read twice, `GEMINI_DAILY_MAX` (15) stays inside the free allowance, and `GEMINI_MODEL` (gemini-3.5-flash-lite) picks the model. It is pinned on purpose: the "latest" aliases can point at slow thinking models that never answer, and two failures in a row stop the reader for the day so a problem cannot use up the allowance. Only public school posts go to Google, never messages or anything private, and Google's free tier may use what it is sent to improve its products. The key is never logged.

School lunch menu (needs GEMINI_API_KEY): set `MENU_PAGE` to the district's menu page, and the schools' own sites if you like (comma separated). The server finds the monthly menu PDF whose file name has "menu" and `MENU_MATCH` (default "elementary"), and reads each new or changed file once with Gemini: one request a month, since the same file linked from several pages is remembered by its contents and a menu that was entered by hand is never read again. Every school day's lunch then goes on the calendar as an all-day entry (the full options, the always-available choices and breakfast are in its details), no-school days such as Fridays are marked "No school", and on school days the Food card shows today's lunch (tomorrow's once it is past 1:30 pm, and on a no-school day it says so and shows tomorrow's). The lunch entries stay off the Today list and the countdown tiles so nothing shows twice. The page is checked every `MENU_HOURS` (6); if Gemini's allowance is out, a menu can be entered by hand into `menu-cache.json` in the data folder and the automation takes over for the following months. It reads the district's public web page the way a browser does, so a renamed file can stop it until the match is adjusted.

Weather: set the location once in Setup under Display, and it uses Open-Meteo (free, no key). The header shows today's weather and, in the gap beside it, a tile each for today and the next two days (icon, high and low, chance of rain). Hover over the tiles for a one line summary of the whole week (the range of highs, which days look wet, frost or heat).

Google Keep shopping list (unofficial, can break): Google has no Keep API for personal accounts, so `server/keep.js` speaks the private protocol the Keep app uses (ported from the open source gpsoauth and gkeepapi). Use a dedicated Google account that the list is shared with, never your main one. Get a master token for that account (see the gpsoauth project: `exchange_token` with the `oauth_token` cookie from accounts.google.com/EmbeddedSetup) and set `KEEP_EMAIL`, `KEEP_MASTER_TOKEN` and `KEEP_LIST` (the list's exact title) in the env file. The list is expected to work like this: category headers stay unchecked, items sit under a header, checked means bought, unchecked means on the list. The board then shows only the unchecked items. An item added on the board first unchecks an existing item with the same name (emoji and case are ignored), and only creates a new one if nothing matches, under the category its words fit, else "Other". Checking on either side checks on the other. Removing an item on the board checks it in Keep and never deletes Keep history. An item deleted in Keep leaves the board. It syncs every `KEEP_MINUTES` (2) and a few seconds after a grocery change. `KEEP_HEADERS` names headers that have no items yet, so they are not mistaken for items. `KEEP_DRYRUN=1` only logs what would change. The token is a long-lived credential: keep it in the env file, never in the repo, and revoke it by removing the account's access to the list or changing that account's password.

Text alerts to the parents (Textbelt): set `TEXTBELT_KEY` and `SMS_TO` (the parents' phone numbers, comma separated) in the env file. The server then texts when a chore needs approval ("Ava finished Homework and Make bed. Needs your OK.", sent after `SMS_APPROVE_DELAY_MIN` minutes, 60 by default, and only for chores still waiting then, so approving on the board in time means no text), when a reward is cashed in, and, if `SMS_REMIND_AT=HH:MM` is set (board time), once a day with who still has daily chores left. Bursts are combined into one text, repeats within 10 minutes are dropped, `SMS_DAILY_MAX` (12) caps texts per day, and a text warns when credits run low. `SMS_DRYRUN=1` only logs. Each text uses one Textbelt credit per parent. The key and the numbers are secrets: keep them in the env file, never in the repo, and they are only ever logged masked.

Backups: the server copies the board to `<data dir>/backups/board-<UTC time>.json` at start and every 6 hours, skips it when nothing changed, and keeps the newest 28. Set `BACKUP_HOURS` (0 turns it off) and `BACKUP_KEEP` to change that. To restore, stop the container and copy a backup over `board.json`.

## Android

The APK is rebuilt only on request, not after every UI change. Until then the app keeps the page it was built with, unless it points at the home server below.

```
cd android && bash gradlew assembleDebug
```

APK lands in `android/app/build/outputs/apk/debug/`. In Setup, More, "Home server" points the app at the Docker server so every screen shares one board. CI uploads the APK as a build artifact.
